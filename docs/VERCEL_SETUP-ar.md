# تجهيز الراية الدمشقية والمطاعم الأخرى على Vercel

النسخة مبنية على أحدث `main` وقت المراجعة، commit `fad6aab`، مع الحفاظ على تحديثات إيقاف المطاعم والحسابات وإعادة الطلب والتوصيل. تجهيز البناء والترحيلات تم اختباره محليًا. النشر الفعلي يحتاج قاعدة بيانات أونلاين ورابط الموقع.

## القيم المطلوبة قبل النشر

| المتغير | المطلوب |
|---|---|
| `DATABASE_URL` | رابط PostgreSQL أونلاين. للتطبيق على Neon استخدم رابط الاتصال المجمع الذي يحتوي `-pooler` في اسم المضيف. لا تستخدم رابط قاعدة البيانات المحلية. |
| `APP_URL` | أصل الموقع المنشور كاملًا، مثل `https://your-domain.com`، دون مسار. يستخدم في رموز QR. |
| `DATABASE_MIGRATION_URL` | اختياري: رابط مباشر لنفس قاعدة البيانات لتنفيذ الترحيلات. إذا لم تضفه، يستخدم البناء `DATABASE_URL`. |

يدعم Neon الاتصال المباشر والمجمع؛ الاتصال المجمع مناسب عندما ينشئ التطبيق اتصالات متزامنة كثيرة، كما توضح [وثائق الاتصال الرسمية](https://github.com/neondatabase/website/blob/main/content/docs/get-started/connect-neon.md).

## إعدادات لها قيم جاهزة

| المتغير | القيمة الافتراضية | الاستخدام |
|---|---|---|
| `DB_POOL_MAX` | `5` | أقصى اتصالات لكل نسخة تشغيل من التطبيق. ليست حدًا لكل مشروع Vercel. |
| `SESSION_TTL_DAYS` | `30` | مدة جلسة الحساب. |
| `LOG_LEVEL` | `info` | سجل الطلبات والأخطاء. |
| `ORDER_IP_RATE_LIMIT` | `600` | محاولات إنشاء الطلب من عنوان واحد خلال 10 دقائق؛ يحسب المحاولات وإعادة المحاولة. |
| `ORDER_PHONE_RATE_LIMIT` | `8` | طلبات جديدة لكل موبايل خلال 10 دقائق. إعادة نفس الطلب لا تستهلك مرة إضافية. |
| `QUOTE_IP_RATE_LIMIT` | `1200` | مراجعات السعر من عنوان واحد خلال دقيقة. |
| `ALERT_WEBHOOK_URL` | فاضي | اختياري: رابط Webhook (Slack أو Discord أو Telegram `sendMessage`) يوصلك عليه تنبيه فوري لما يحصل خطأ غير متوقع أو تفشل المهمة الدورية. |
| `CRON_SECRET` | فاضي | اختياري: كلمة سر عشوائية طويلة (32 حرف أو أكتر) للمهمة الدورية `/api/cron/maintenance`. نفس القيمة بتتحط في GitHub Secrets (شوف دليل الطوارئ). |

لا يحتاج المشروع `AUTH_SECRET` أو بوابة دفع خارجية: الجلسات محفوظة في PostgreSQL والتحويل بإنستاباي يراجعه موظف المطعم يدويًا.

## خطوات الإعداد

1. أنشئ قاعدة PostgreSQL في Frankfurt لتكون قريبة من وظائف التطبيق المضبوطة على `fra1`.
2. اربط المستودع بـ Vercel واختر Next.js. أمر البناء المحدد في المشروع هو `npm run vercel-build`؛ ينفذ الترحيلات ثم يبني التطبيق. اختر إصدار Node مدعومًا يحقق `>=20.9`.
3. أضف `DATABASE_URL` و`APP_URL` إلى Production. استخدم قاعدة مستقلة أو فرع قاعدة بيانات مستقل لـ Preview، وكذلك رابط الترحيلات الخاص بها عند استخدامه. كل بناء يطبق الترحيلات على قاعدة بيئته.
4. انشر Preview أولًا وجرب التسجيل وحفظ المنيو وطلبات الكاش وإنستاباي وتتبع الطلبات.
5. أنشئ مدير المنصة مرة واحدة من جهازك بالأمر `npm run db:seed` بعد ضبط `DATABASE_URL` لقاعدة الإنتاج و`SEED_ADMIN_EMAIL` و`SEED_ADMIN_PASSWORD` و`SEED_DEMO=false` في ملف بيئة محلي. لا تُرسل كلمة المرور في دردشة أو تضف ملف البيئة إلى المستودع. هذه متغيرات التهيئة مرة واحدة؛ البناء لا ينشئ حسابات تجريبية.
6. من إدارة المطاعم أضف اسم المطعم بالعربي والإنجليزي، الباتش، الصور، المنيو، فريق العمل، نقطة الاستلام، الدفع ومواعيد العمل ووقت التحضير.
7. اضبط `APP_URL` على رابط HTTPS النهائي وأعد النشر قبل تنزيل QR للطباعة. جرب الملصق المطبوع بكاميرات موبايلات مختلفة.

في Vercel يمكن تخصيص قيم مختلفة لـ Production وPreview، وتغيير متغير بيئة يحتاج نشرًا جديدًا حتى يسري. [وثائق Vercel](https://vercel.com/docs/environment-variables).

## التحقق قبل تشغيل الطلبات الحقيقية

جرب على رابط Preview ضغط 100 طلب متزامن باستخدام مطعم اختبار، ثم ضغطًا مستمرًا مع أجهزة مطعم مفتوحة والتتبع؛ قارن سرعة الطلبات وحدود اتصالات قاعدة البيانات والأخطاء. سكريبت الاختبار الموجود في المشروع يرفض قواعد البيانات البعيدة لحماية الطلبات الحقيقية، لذلك اختبار الاستضافة يحتاج بيئة اختبار مستقلة وأداة مخصصة لها.

فعّل مراقبة `/api/ready` وسجل الأخطاء، واضبط النسخ الاحتياطي لقاعدة البيانات. نفّذ يوم تشغيل صغير مع الموظفين لضبط أوقات التحضير والتوصيل وتجربة صوت الطلبات والطابعة. إنستاباي يحتاج مراجعة وصول المال فعلًا قبل الضغط على تأكيد الدفع.

## قائمة التجهيز النهائية (أكتوبر 2026)

| الخدمة | الخطة | ليه |
|---|---|---|
| GitHub | الحالية | الكود موجود في `youssefelsane-hash/ANU_Essen`. |
| Vercel | **Pro** (حوالي 20 دولار شهريًا) | خطة Hobby المجانية للاستخدام الشخصي غير التجاري فقط، والمشروع ده تجاري (عمولة على المبيعات). |
| Neon (PostgreSQL) | مجاني للتجربة، **مدفوع قبل الطلبات الحقيقية** | المجاني فيه 100 ساعة تشغيل في الشهر. شاشة المطعم بتتزامن كل 3 ثواني، فالقاعدة مش بتنام طول ما المطعم فاتح (12 ساعة يوميًا ≈ 90 ساعة شهريًا). لو الحد خلص، القاعدة بتقف والطلبات تقف. |
| دومين (اختياري) | أي مسجّل دومينات | رابط أوضح على البوستر من `*.vercel.app`. |

### المتغيرات في Vercel → Project → Settings → Environment Variables (اختار Production)

| المتغير | القيمة |
|---|---|
| `DATABASE_URL` | من Neon: زرار **Connect** → فعّل **Connection pooling** → انسخ الرابط زي ما هو (بيبدأ بـ `postgresql://` وفيه `-pooler`). |
| `DATABASE_MIGRATION_URL` | نفس الشاشة لكن **اقفل** Connection pooling وانسخ الرابط (من غير `-pooler`). |
| `BOOTSTRAP_ADMIN_EMAIL` | إيميلك اللي هتدخل بيه كسوبر أدمن. |
| `BOOTSTRAP_ADMIN_PASSWORD` | كلمة سر قوية 12 حرف أو أكتر. بتتستخدم مرة واحدة بس لإنشاء أول حساب. |
| `APP_URL` | بعد أول نشر ناجح: رابط الموقع، مثلًا `https://anu-essen.vercel.app` (حتى لو نسيت `https://` السيستم بيكمّلها). |

مش محتاج تشغّل أي أمر على جهازك: كل نشر بيعمل الجداول، ويظبط الأدوار والصلاحيات، ولو مفيش سوبر أدمن بيعمله من المتغيرين `BOOTSTRAP_*`. لو فيه سوبر أدمن بالفعل، المتغيرين بيتجاهلوا ومش بيغيروا أي كلمة سر.

لو النشر فشل، آخر سطر في Build Logs بيقول السبب بالظبط من غير ما يطبع كلمة السر، مثلًا: «DATABASE_URL is not set» أو «wrong database user or password».

### بعد أول نشر ناجح

1. افتح `https://رابط-موقعك/login` وادخل بإيميل وكلمة سر السوبر أدمن.
2. امسح `BOOTSTRAP_ADMIN_PASSWORD` من Vercel (اختياري لكن أأمن).
3. حط `APP_URL` برابط الموقع واعمل Redeploy عشان الـQR يطلع بالرابط الصح.
4. من لوحة الإدارة: Restaurants → أضف المطعم، المنيو، نقاط الاستلام (بوابة الجامعة توصيل افتراضي — «استلام من المطعم» بيتعمل لوحده)، إنستاباي، مواعيد العمل، الموظفين.
5. جرّب طلب كامل من موبايلك (كاش وإنستاباي) قبل طباعة البوستر.
